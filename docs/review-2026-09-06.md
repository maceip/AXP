# Engineering review · September 6, 2026

## Assessment

AXP has a coherent core worth keeping: an AHP-compatible host,
a separate ACP executor, Git-bound artifacts, and clients that share that host
for state and permissions. TypeScript, React and SQLite are a
reasonable fit for this developer preview. A framework replacement, extra
service tier, load balancer or container orchestrator would not fix the main
problems found here.

The pre-review tree had concrete recovery bugs and unnecessary work on hot
paths. Its documentation also asked newcomers to become operators before they
could understand the project. This review fixes those issues and preserves the
existing permission model. It does **not** make AXP ready for a public,
multi-user website or implement the proposed AXP community onboarding.

Scope: source under `src/`, browser source, CLI/package entry points, protocol
schemas and upstream boundary, tests, examples, deployment scripts and project
documentation. Baseline: `94544e919c0a2196615ffc484ae56c58421cc34b`.
The resulting package version is 0.3.1; wire negotiation remains AXP 0.2.0.
This is a self-review with runtime regression evidence, not an independent
security audit or a review performed by Google or Microsoft.

## Architecture and cohesion

The host transaction remains synchronous and commits state, events and
receipts before notifications. None of the optimizations defer accepted writes
or weaken permission/lease checks. Full upstream AHP reducer fixtures and schema
bytes remain intact. The browser still receives neither provider credentials
nor signing keys, and AAMP still cannot approve agent tools by email.

A shared `channel-state.ts` removes duplicated reducer routing. Browser command
translation has a separate lifetime and module from the gateway's HTTP/cache
work. The React shell, workspace panels, contribution controls, transcript and
stored-content rendering now have separate components. This reduces the cost
of modifying a feature without introducing a general plugin framework.

Every workspace refresh checks that the host is reachable, even when cached
content is available; disconnect clears connection state and
recovery fetches fresh snapshots. The existing silent-socket regression remains
necessary even when cached content looks healthy.

The visual direction stays close to Huabu's calm, persistent workspace. Pierre
handles diffs and file navigation; Git handles checkpoint, verification and
publication semantics. The review keeps the working desktop/phone layouts,
fixes navigation/focus/error states, and makes output inspectable. It does not
substitute a new design system for the product's unfinished community model.

## Performance evidence

Same Apple M5 Max, macOS arm64, Node 24.15.0, dependencies and benchmark source;
one warmup followed by seven measured batches. Baseline code was extracted to
an isolated directory rather than resetting the working checkout.

| Workload                                  | Before, median | After, median |
| ----------------------------------------- | -------------: | ------------: |
| Validate 20,000 chat delta actions        |      105.76 ms |       0.64 ms |
| 100 expiry ticks with 1,000 idle sessions |      316.35 ms |      54.81 ms |

Run `npx tsx scripts/benchmark.ts`. [Raw measurements](evidence/review-performance.json)
include minimum/maximum samples. This is an in-memory CPU benchmark, not a disk,
network, provider or production-throughput benchmark.

A real ACP process emits 100 text chunks while its satellite makes five
snapshot subscription RPCs, including setup. A separate gateway test applies
100 updates with **zero additional snapshot subscriptions** and compares its
result to the host's exact chat state. These checks protect a scaling property
rather than imposing a timing threshold on shared CI machines.

The initial browser JavaScript is approximately 397 KB / 121 KB gzip; the lazy
diff renderer is approximately 735 KB / 207 KB gzip, with a separate lazy WASM
asset of approximately 622 KB / 232 KB gzip. Hashed static assets can be cached;
API data and HTML remain private/no-store. Large lazy chunks still cost time on
first open. No bundle-size warning was hidden and no slow-network timing claim
is made. Completed Markdown is memoized to avoid reparsing unchanged history.

## DX and documentation

The README now states the implementation language and offers a local first
experience with no account, provider key, donated compute or host setup. The
sample workspace is labelled as sample data. Setting
up one's own repository is an advanced path, not the explanation of AXP.

Dedicated guides cover [first use](getting-started.md), [agent setup](agent-setup.md),
[SDK contracts and retries](sdk.md), [CLI precedence and lifetimes](cli.md),
[architecture](design.md), [workspace limits](workspace.md) and
[operations](linux-hosting.md). Contribution guidance leads with useful work
and reproducible evidence, rather than a target test count. Existing live-model
receipts keep their original dates and scope; they are not represented as a fresh
provider run during this review.

## Validation

Local verification on the reviewed implementation:

- Strict TypeScript, ESLint, formatting, distributable build and complete core
  suite pass: 338 tests, including the unchanged upstream fixture corpus.
- Pure AXP reducer branch and line coverage remain 100%. This is deliberately
  scoped coverage, not a claim of 100% coverage across the application.
- Seven Chromium workflows pass, including a real ACP edit, exact-commit Git
  verification, contributor signature and independent maintainer approval.
  Accessibility assertions and desktop/phone screenshot inspection are included.
- Three operations tests pass, including live-WAL restoration and incomplete
  backup rejection. The deterministic process/Git demo, schema drift check and
  fresh tarball installation smoke test pass.
- `npm audit` reported no known dependency vulnerabilities for the installed
  dependency tree at review time; that is not proof that the software is free
  of security defects.

[CI](https://github.com/maceip/AXP/actions/workflows/ci.yml) runs the exact commit
on Linux, macOS and Windows, plus Chromium, offline-container ACP and a real
systemd/Caddy lifecycle in a disposable Linux container. Its results are the
source for cross-platform status; a local macOS pass is not substituted for it.
No production domain, VM, mail service or provider account was changed by this
review.

## Remaining limits and next decision

The following limits remain:

- The public identity/session gateway is unimplemented. Today's browser gateway
  is personal and loopback-only. It must not be exposed as one shared privileged
  account to implement community signup.
- SQLite still rewrites channel JSON snapshots; audit and receipts grow without
  automatic retention. Full catalog and audit reads are not wire-paginated.
  UI paging alone does not prove large-fleet capacity. Measure long histories
  and concurrent contributors before promising that scale.
- Native agents run with user privileges; POSIX process groups cannot contain a
  deliberately detached process. Hard provider spending caps and trustworthy
  remote execution need their own boundaries.
- Browser testing covers Chromium desktop/phone sizes, not Safari, Firefox or
  real-device mobile performance. Historical live-provider evidence is linked
  separately in [Validation](validation.md).
- Local backup verification does not test recovery after losing the machine,
  production TLS/mail availability or multi-host failover. Primitive systemd,
  Caddy and verified snapshots remain the intended operating model for now.

The next proposed product change is [AXP-first community onboarding](community-onboarding-proposal.md):
join the official project without donating agent time, optionally contribute an
avatar, and receive recognition. Account provisioning, automatic connection,
image tasks, credits and publication have **not** been implemented. Owner
approval of this review is the boundary before that work begins.
